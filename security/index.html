AEOWUN // TRUST CENTER

HOW THE SOFTWARE WORKS.

Trust is easier when the important parts are visible: where data goes, what a tool is allowed to do, how changes are checked, and what stage the software is actually in.

01 // DATA

LOCAL WHERE IT MAKES SENSE.

AEOPIN and CheckMaker are local-first Windows applications. Their core workflows do not require an account or a cloud service. MAGY can also be configured around local models and local model servers, while other MAGY configurations can use external model providers. The model provider is a configuration choice; the runtime boundary is part of MAGY itself.

02 // AUTHORITY

A MODEL IS NOT THE RUNTIME.

MAGY separates model reasoning from execution. A model can propose a tool call or other action, but the runtime decides what is permitted inside the project boundary. Restricted writes and commands can require operator approval.

03 // VERIFICATION

CHECK THE RESULT.

A completion message is not proof that work succeeded. MAGY can run configured verification after changes and use the resulting output as evidence about the state of the project. The quality of that evidence still depends on the checks configured for the project.

04 // PRODUCT BEHAVIOR

NARROWER CHANGES ARE EASIER TO TRUST.

CheckMaker is one example. A checkbox change is handled as a targeted byte-level write instead of rewriting the whole Markdown file. AEOPIN's installation system verifies the expected payload before allowing the managed application to be installed. Different projects use different techniques, but the goal is the same: make important behavior explicit and bounded.

05 // COMMUNICATION

SAY WHAT EXISTS.

AEOWUN labels projects according to their actual state: shipped, active development, alpha, experimental, research, or archived. A working prototype is not described as a finished service, and an idea is not described as a product just because there is code behind it.

WHAT THIS MEANS

TRUST IS NOT A CLAIM.

No software is automatically trustworthy because its author says it is. The useful question is what the system actually does: what it can access, what it changes, what it refuses to do, and what evidence exists after an operation.

That is why AEOWUN publishes working software, source code, engineering notes, release status, and known limitations where practical.
