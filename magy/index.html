MAGY

AI-assisted software engineering with a controlled runtime. Models propose work. MAGY decides what can actually happen, executes it within defined boundaries, and verifies the result.

READ THE ARCHITECTURE VIEW SOURCE
THE IMPORTANT PART

THE MODEL IS NOT THE AUTHORITY.

MAGY separates intelligence from execution. A model can reason about a task and propose what to do. The MAGY runtime controls the available tools, the project boundary, approvals, writes, and commands. The model does not get to redefine those rules.

MODEL LAYER

MORE THAN ONE CONFIGURATION

MAGY can be configured around different model providers and model sizes. Local models are one path, including the smaller local models AEOWUN may package for its own builds. Other configurations can use OpenAI or ChatGPT-backed models.

RUNTIME

THE SYSTEM AROUND THE MODEL

Models provide reasoning and proposals. The runtime handles tool calls, workspace access, approvals, state transitions, and execution boundaries.

VERIFICATION

CHECK THE RESULT

After a change, MAGY can run configured verification and use the resulting output to determine whether the task actually succeeded.

THE LOOP

FROM REQUEST TO VERIFIED RESULT.

01 DEFINE

Load a project and describe the work you want done.

02 REASON

A configured model analyzes the task and proposes an action.

03 CONTROL

MAGY checks the requested operation against its runtime rules.

04 EXECUTE

Approved work runs through controlled tools inside the project boundary.

05 VERIFY

The result is checked instead of being accepted because the model says it worked.

HONEST STATUS

ACTIVE DEVELOPMENT.

MAGY is still being developed and currently exists in several configurations. It is not presented as a finished autonomous engineering service. The system is being built around a simpler question: how much useful work can an AI system do when the runtime, rather than the model, remains responsible for what actually happens?

BOUNDARIES

WHAT MAGY DOES NOT GUARANTEE.

MAGY does not make a model correct. It does not turn model output into authority. It does not silently approve restricted actions, and it does not treat a model's completion message as proof that the work succeeded.

Verification still depends on the checks available to the project and on whether those checks meaningfully test the requested result.
